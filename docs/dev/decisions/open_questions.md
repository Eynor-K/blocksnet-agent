# Архитектурные вопросы рефакторинга — решения

Статус: **закрыты рекомендациями ревью от 2026-07-21** (см. [review.md](review.md)).
Решения приняты по коду, а не по намерению; каждое сопровождается основанием
и указанием, что произойдёт, если решить иначе. Игорь может отменить любое —
тогда правится соответствующий шаг в [implementation/](implementation/).

Q1–Q3 были в исходном черновике. Q4–Q7 добавлены по итогам сверки с кодом:
без них план не исполним.

| # | Вопрос | Решение |
|---|---|---|
| Q1 | A2A-библиотека | `a2a-sdk`, версия пиниться после спайка |
| Q2 | Стратегия skills | Два skill, `analyze_urban_question` — обёртка над общим ядром |
| Q3 | Моно- или мульти-репо | Моно-репо, два Dockerfile |
| Q4 | Состояние tools в MCP | Явные сессии `session_id` + TTL/LRU |

## Q1. `a2a-sdk` vs собственный JSON-RPC

### Решение: `a2a-sdk`, с обязательным спайком до старта этапа

Аргументы исходного черновика в силе: проект уже зависит от `mcp`, `pydantic`,
`langchain-core`, `geopandas`; соответствие спеке критично, потому что вторая
сторона интеграции (MAS) реализует A2A не по нашей документации.

Что добавлено к рекомендации:

1. **Спайк обязателен** ([00-preflight.md](../plans/a2a_refactor/00-preflight.md), шаг 0.6).
   Exit-критерий: локально поднимается reference-сервер SDK, отдаёт Agent Card,
   принимает `message/send`. Пока это не воспроизведено — этап 05 не стартует.
2. **Версия пинится точно** (`a2a-sdk==X.Y.Z`), не диапазоном. SDK молодой,
   ломающие изменения между минорными версиями вероятны.
3. **Ссылка на спеку исправлена**: канонический репозиторий —
   `https://github.com/a2aproject/A2A` (ранее `google/A2A`). Ссылка в исходном
   черновике (`a2a-protocol/a2a-spec`) не проверялась; проверить при спайке.
4. **Граница изоляции**: весь код SDK живёт только внутри
   `blocksnet_agent/a2a/`. Ядро агента про A2A не знает. Если SDK не подойдёт,
   заменяется содержимое одного пакета.

**Если решить иначе (свой JSON-RPC):** +3–5 дней, и придётся самим
поддерживать Agent Card, task lifecycle, artifact streaming, push notifications.
Оправдано только если спайк провалится.

## Q2. Convenience skill + multi-step, или только multi-step

### Решение: два skill, но одна реализация

Оба skill объявляются в Agent Card:

- `run_pipeline` — основной, task lifecycle, `TaskStatusUpdateEvent`, артефакты;
- `analyze_urban_question` — convenience, **тонкая обёртка**: запускает
  `run_pipeline` и ждёт терминального статуса, отдаёт тот же JSON, что сегодня.

Уточнение к исходной рекомендации: черновик допускал два независимых пути
исполнения («convenience skill — 10 строк вокруг `agent.run()`»). Это дало бы
два места, где чинить дедлайны, прогресс, ошибки и сериализацию. Реализация
одна, различается только режим ожидания (блокирующий vs потоковый).

Основание для сохранения convenience skill — обратная совместимость: контракт
`analyze_urban_question` зафиксирован в [tool_contract.md](../../tool_contract.md)
и покрыт тестами (`test_tool_contract.py`, `test_async_mcp_contract.py`,
`test_serialize.py`).

## Q3. Моно-репо vs мульти-репо

### Решение: моно-репо (без изменений)

Аргументация исходного черновика принята полностью: маленькая команда,
частые перекрёстные правки, много общего кода (`serialize`, `config`, модели
данных). Разделение по image — через два Dockerfile.

Уточнение: разделение зависимостей делается через `pyproject.toml` с extras
(`.[agent]` / `.[mcp]`), потому что `pyproject.toml` в репозитории сейчас
отсутствует, а один `requirements.txt` затащит `langchain`, `langgraph`,
`optuna`, `tiktoken` в MCP-образ, где они не нужны. Это задача этапа Docker,
а не блокер.

**Пересмотреть, когда** появится второй внешний потребитель MCP-server
(не наш агент) или отдельный релизный цикл.

## Q4. Состояние: как MCP исполняет tools, замкнутые над `state` (НОВЫЙ)

### Контекст

Инструменты создаются фабрикой `make_tools(state, data_dir, output_dir)` и
замыкаются над мутабельным словарём `state`. `compute_*` пишут в
`state[result_key]`, а `get_analysis_results`, `get_metric_for_block`,
`render_metric_map`, `list_cached_data` читают оттуда. Stateless-экспозиция
даёт «Кэш пуст» на 12+ инструментах (детали — [review.md](review.md), R1).

### Варианты

**A. Один глобальный `state` на процесс MCP.** Просто, но параллельные клиенты
затирают данные друг друга; `list_cached_data` показывает чужое; память не
освобождается (GeoDataFrame'ы тяжёлые).

**B. Сессия на MCP-соединение.** Естественно для stdio (один клиент — одно
соединение), но не переносится на HTTP-транспорт из MAS-плана и не даёт
клиенту управлять временем жизни.

**C. Явный `session_id` в аргументах + SessionStore с TTL/LRU.**

### Решение: вариант C

- `blocksnet_mcp/session.py`: `SessionStore` c `get_or_create(session_id)`,
  TTL (`SESSION_TTL_SEC`, по умолчанию 1800) и LRU-лимитом
  (`MAX_SESSIONS`, по умолчанию 8).
- Каждый MCP-tool получает дополнительный параметр
  `session_id: str = "default"`; значение по умолчанию сохраняет
  однопользовательский сценарий рабочим без изменений на стороне клиента.
- Служебные tools: `open_session`, `close_session`, `session_info`.
- В конверте ответа всегда возвращается фактический `session_id` — клиент
  может не передавать его первым вызовом и подхватить из ответа.

Обоснование: единственный вариант, работающий и для stdio, и для HTTP,
и для MAS (где `session_id` естественно склеивается со `scenario_id`).
Стоимость — один параметр в сигнатуре, прокидываемый обёрткой автоматически.

**Явное ограничение v2.0:** сессия живёт в памяти одного процесса.
Горизонтальное масштабирование MCP (несколько реплик за балансировщиком)
требует sticky-сессий или внешнего стора — вне объёма, зафиксировано в
[09-deferred.md](../deferred/a2a_refactor_deferred.md).

## Q5. Формат выхода MCP-tools (НОВЫЙ)

### Контекст

Все 30 доменных инструментов объявлены `-> str` и возвращают человекочитаемый
русский текст; ошибки — тоже строки. Агент парсит эти строки в `metrics.py`
и `hypotheses.py`. Исходный план требовал «JSON Schema для каждого tool» и
«валидный JSON» на выходе.

### Решение: строка остаётся, конверт добавляется, схема — только на вход

MCP возвращает:

```json
{
  "status": "ok",
  "tool": "compute_service_provision",
  "session_id": "s-1",
  "text": "<исходная строка инструмента>",
  "artifacts": ["outputs/run-.../map.png"],
  "error_code": null
}
```

- `status` = `failed`, если строка начинается с `FAILURE_MARKERS`
  (`blocksnet_agent/metrics.py`) — классификация уже реализована в
  `_failed_observation` (`blocksnet_agent/tools/__init__.py`),
  переиспользуется, не дублируется.
- JSON Schema **входа** генерируется FastMCP автоматически из сигнатуры —
  дополнительной работы не требует.
- `text` не переформатируется: любое изменение строк ломает парсеры агента.

**Структурированный выход** (`data: {...}` рядом с `text`) — отложен в v2.1
как per-tool opt-in: инструмент объявляет `to_structured(result)`, остальные
работают по-старому. Одномоментное переписывание 30 инструментов — регресс
в агенте с высокой вероятностью и нулевой выгодой на этом этапе.

## Q6. Топология: агент вызывает MCP или они — соседи (НОВЫЙ)

### Контекст

Исходная архитектура: A2A-агент → MCP → tools. Но `state`, который пишут
tools, читает не только агентский цикл, а и постобработка: `overlay_candidates`,
численная верификация гипотез, `confidence_basis`, `valid_block_ids`
(детали и ссылки на строки — [review.md](review.md), R2). Граница процесса
между tools и агентом рвёт эти связи **тихо**: без исключений, с деградацией
качества ответа.

### Решение: sibling-топология

```text
             ┌───────────────┐        ┌───────────────┐
 A2A-клиент →│  A2A-агент    │        │  MCP-server   │← MCP-клиент
             │  (агент, LLM) │        │  (без LLM)    │
             └───────┬───────┘        └───────┬───────┘
                     │                        │
                     └──── make_tools() ──────┘
                        общая фабрика, у каждого
                         процесса — свой state
```

- Агент исполняет tools **в своём процессе**, как сейчас. `agent.py` не
  меняется, регресса нет.
- MCP-server — независимый потребитель той же фабрики со своим SessionStore.
- Общая точка правды — `blocksnet_agent/tools/catalog.py` (шаг
  [01-tool-catalog.md](../plans/a2a_refactor/01-tool-catalog.md)): и агент, и MCP
  получают набор инструментов одним вызовом.

Что при этом всё равно достигается из целей reasoning.md:

| Цель | Достигается? | Как |
|---|---|---|
| Переиспользование tools внешними агентами | да | MCP экспонирует все 32 |
| Новый tool = 1 файл | да | попадает и в агента, и в MCP |
| LLM-конфиг не обязателен для MCP | да | MCP не импортирует `llm.py`; agent-tool ленивый (Q7) |
| Deterministic-режим для CI | да | прямой вызов MCP-tool |
| Агент развивается независимо | да | A2A-слой изолирован |
| Агент и tools в разных контейнерах | **нет** | отложено, см. ниже |

**Отложено, не отменено.** Режим `MCP_TOOL_PROXY=1` (агент ходит в MCP по сети)
остаётся целью, но требует отдельного дизайна: перенос `result_key`-данных
через границу процесса либо вынос постобработки (overlay/hypotheses) на
сторону MCP. Оценка — отдельный этап, не входит в этот рефакторинг.
Зафиксировано в [09-deferred.md](../deferred/a2a_refactor_deferred.md).

## Q7. Судьба `analyze_urban_question` как MCP-tool (НОВЫЙ)

### Контекст

Исходный план удалял его из MCP (шаг 2.4). От него зависят 6 мест: реэкспорт
пакета, два теста, smoke-клиент, раннер примеров, `city_picker.py`
(перечень — [review.md](review.md), R8).

### Решение: остаётся под флагом, помечен deprecated

- Код переезжает в `blocksnet_mcp/agent_tool.py`.
- Регистрация условная: `ENABLE_AGENT_TOOL` (default `true` в v2.0).
- **LLM-настройки читаются лениво**, внутри вызова, а не при импорте модуля.
  Это и есть решение исходной претензии reasoning.md §2.3: MCP-server
  стартует и отдаёт 32 raw tools **без** `CHAT_URL`/`API_KEY`; они нужны
  только если кто-то реально дёрнет agent-tool.
- В описании инструмента — `[DEPRECATED] используйте A2A skill …`.
- Удаление — в v2.1, после миграции примеров и smoke на A2A-клиент.

Строго лучше удаления: претензия закрыта, потребители не сломаны,
переходный период явный.
