## TIER 1 — точечные фиксы (низкий риск, чинят прямые дефекты)

### T1.1 Entity-aware grounding (квартал в вопросе)
**Проблема.** Эксп.2: вопрос «что разместить в квартале 603?», но `get_block_info(603)` не вызван; все метрики — общегородские батчи, выданы за показатели 603 (фактическая ошибка атрибуции).

**Решение.**
1. Перед запуском executor извлекать упомянутые `block_id` из текста вопроса (регэксп `кварт\w*\s*№?\s*(\d+)` + латиница `block\s*(\d+)`).
2. Если найдены — прокидывать в `context` директиву: «Вопрос касается конкретных block_id={…}: обязателен вызов `get_block_info` по каждому и фильтрация всех метрик к этим кварталам; нельзя выдавать городские агрегаты за показатели квартала».
3. Усилить механизм M1 (`_grounding_issue`): если в вопросе/ответе фигурирует конкретный `block_id`, требовать, чтобы он реально присутствовал в аргументах или наблюдении хотя бы одного вызова инструмента — иначе reentry. Сейчас M1 проверяет только числа, а городской агрегат «числа содержит» и ложно проходит.

**Файлы.** `agent.py` (новая `_mentioned_block_ids()`, правка `run()` контекста, правка `_grounding_issue`/`_coherence_issues`), при необходимости — уточнение текста в `prompts.py`.
**Усилие.** ~Средне (полдня). **Риск.** Низкий (добавочная проверка, fail-open: если block_id нет — поведение прежнее).
**Источник.** fp2mp: в системном промпте `get_block_info(block_id)` явно прописан как инструмент проверки гипотез по кварталу.

### T1.2 Хирургический реентри + мемоизация вызовов
**Проблема.** Дубли инструментов (эксп.1 ×2, эксп.2 ×3): `_refine_until_coherent` при каждом заходе заново гоняет ВЕСЬ ReAct-цикл, и LLM повторяет идентичные `(tool, args)`. Лишние токены, время, гора артефактов.

**Решение.**
1. **Мемоизация на уровне (tool, args).** Обёртка инструментов кэширует `(name, args_json)→observation` в `self._state`. Повторный идентичный вызов возвращает прошлое наблюдение без пересчёта и без новой записи артефактов. (Сейчас `state` кэширует данные, но не пары вызов→результат и не подавляет повторную запись CSV/карт.)
2. **Хирургический реентри.** По образцу fp2mp `_verify_unverified_hypotheses`: на реентри передавать модели сводку уже выполненных вызовов и просить дополнить ТОЛЬКО недостающее/проблемные секции, а не повторять весь анализ. Реентри-промпт уже близок — добавить в него блок «Уже выполнено: …» из `steps`.

**Файлы.** `agent.py` (`_refine_until_coherent`, `_build_reentry_prompt`), `tools/__init__.py` или `tools/registry.py` (обёртка-мемоизатор вокруг `make_tools`).
**Усилие.** Средне (день). **Риск.** Средний — мемоизация должна учитывать, что часть инструментов идемпотентна (compute_*), а артефакты не должны перезаписываться повторно. Решается белым списком идемпотентных инструментов.
**Источник.** fp2mp `_verify_unverified_hypotheses` (точечный довызов вместо полного прогона).

### T1.3 Бюджет артефактов для батч-операций
**Проблема.** Эксп.2: `compute_service_provision({service_type:'key'})` сохранил 71 CSV + 35 карт (по файлу на каждый из 34 сервисов ×3 реентри) для вопроса про один квартал — нерелевантный мусор.

**Решение.**
1. Для батч-режима (`key/basic/advanced/comfort`) по умолчанию сохранять только сводную таблицу (`competitive_provision_batch_*.csv`) и НЕ плодить пер-сервисные CSV+PNG, если они не запрошены явно. Пер-сервисные — за флагом `save_per_service=False`.
2. Глобальный потолок артефактов на запуск (например 20 карт) с предупреждением в `run_log`.

**Файлы.** `tools/provision.py` (`_compute_service_batch`), `runtime.py` (счётчик артефактов/потолок), `tools/viz.py` (уважать потолок).
**Усилие.** Низко-средне. **Риск.** Низкий.
**Источник.** CoScientist — дисциплина «минимального набора шагов» оркестратора.

### T1.4 Гарантия ANALYSIS PLAN (починка слияния)
**Проблема.** Эксп.2: в финале нет секции ANALYSIS PLAN (ответ начинается с HYPOTHESES), хотя M3 обязателен. План потерян при `_merge_sections` после реентри либо не восстановлен.

**Решение.**
1. В `_merge_sections` не затирать непустую секцию старого ответа пустой из нового (уже частично так, но проверить порядок и потерю ANALYSIS PLAN при первом ключе).
2. Финальный гейт в `_parse_output`: если ANALYSIS PLAN пуст после всех проходов — либо синтезировать его из выполненных вызовов (как `_build_reflection`), либо явно пометить в LIMITATIONS «plan missing». Не отдавать ответ молча без плана.

**Файлы.** `agent.py` (`_merge_sections`, `_parse_output`, опц. новая `_build_plan_fallback`).
**Усилие.** Низко. **Риск.** Низкий.
**Источник.** внутренний баг (выявлен анализом).

### T1.5 Единый источник confidence
**Проблема.** LLM пишет CONFIDENCE 0.9/0.8 в секции, а система перетирает авто-скорингом 0.78 — в логах два разных числа, путает.

**Решение.**
1. Убрать CONFIDENCE из обязательного формата вывода LLM ИЛИ переименовать его в «self_confidence» и в итог класть только авто-скоринг.
2. В `run_log` показывать оба явно: `confidence (scored)=… / self_reported=…`.
3. Опционально: подключить реальный учёт токенов (callback) вместо tiktoken-оценки — для честной стоимости прогона.

**Файлы.** `prompts.py` (формат), `agent.py` (`_parse_output`, `_extract_sections`), `runtime.py` (`write_run_log`); опц. новый `usage.py` по образцу fp2mp.
**Усилие.** Низко (без токенов) / средне (с токенами). **Риск.** Низкий.
**Источник.** fp2mp `usage.py` (real vs estimate, авторитетный итог отдельно от лога).

## TIER 2 — качество рассуждения (средний риск, повышают валидность вывода)

### T2.1 Стадия гипотез ДО анализа (hypothesis-first)
**Проблема.** Эксп.1: натянутая интерпретация (центральность подана как довод «за размещение школ» без причинной связи); план и гипотезы формируются постфактум под уже посчитанное.

**Решение.** Ввести явный предварительный шаг: из вопроса сгенерировать 2–5 проверяемых гипотез с указанием, какой инструмент/метрика каждую проверяет, ДО массовых `compute_*`. Затем ReAct исполняет именно эти тесты. Это дисциплинирует выбор метрик (релевантность) и убирает «метрику ради метрики».

**Файлы.** `agent.py` (новый под-шаг перед `executor.invoke`, либо усиление промпта ANALYSIS PLAN, чтобы план = гипотезы+тесты), `prompts.py`.
**Усилие.** Средне. **Риск.** Средний (доп. LLM-вызов; нужно следить за стоимостью). **Источник.** CoScientist HypothesesAgent (2–5 testable hypotheses как отдельная стадия).

---

### T2.2 Лёгкий self-critic перед финалом
**Проблема.** Внутренние противоречия не отлавливаются: эксп.1 одновременно советует «центральные» и «нулевой обеспеченности» кварталы, не примиряя критерии и не давая единого приоритета.

**Решение.** Один домен-нейтральный критик-проход (по образцу fp2mp `critic`): проверяет согласованность RESULT↔REFLECTION↔HYPOTHESES, наличие единого приоритизированного вывода, отсутствие противоречащих списков без объяснения. При нарушении — один реентри с конкретной претензией (вписывается в существующий бюджет `_MAX_REENTRY`).

**Файлы.** `agent.py` (новая `_consistency_critic`, вызов в `_coherence_issues`).
**Усилие.** Средне. **Риск.** Средний (доп. LLM-вызов; уже есть инфраструктура реентри). **Источник.** fp2mp `nodes/critic.py`.

---

### T2.3 Защита от неинформативной статистики
**Проблема.** Эксп.1: «средняя совместная обеспеченность 2180.44» вынесена в RESULT, хотя при медиане 0, std≈35424, max=598000 среднее не интерпретируемо.

**Решение.** В наблюдениях инструментов (`compute_shared_provision` и др.), где сильный перекос (`std ≫ |mean|` или `mean ≫ median`), добавлять в текст наблюдения пометку «⚠ распределение скошено: опирайся на медиану/перцентили, не на среднее». Модель получает подсказку прямо в данных.

**Файлы.** `tools/provision.py` (форматтер сводки), при необходимости `tools/services.py`, `tools/network.py`.
**Усилие.** Низко-средне. **Риск.** Низкий. **Источник.** наблюдение анализа + дух fp2mp `summarize.py` (числобережное сжатие).

---

### T2.4 Задействовать цикл «гипотеза развития → тест»
**Проблема.** Оба эксперимента дают качественные рекомендации («разместить рестораны/школы»), но не измеряют эффект, хотя в `optimize.py` уже есть `propose_zone_development` (TPE) и `compute_scenario_provision` (before/after). Они ни разу не вызваны.

**Решение.** Для генеративных вопросов («что/где разместить/построить») в плане требовать измеренный вывод: `suggest_target_blocks → propose_zone_development → compute_scenario_provision` с before→after по `block_id`. Не жёсткий пайплайн, а директива в промпте + capability-card, чтобы агент выбирал сам.

**Файлы.** `prompts.py` (директива для девелоперских вопросов), опц. карточка в `data/blocksnet_kb/`, проверка в `agent.py` (если вопрос генеративный, но scenario-теста нет → follow-up/limitation).
**Усилие.** Средне. **Риск.** Средний (TPE-оптимизатор дороже по времени). **Источник.** fp2mp README «цикл гипотеза развития → тест» + `tools/blocksnet/optimize.py`.

---

### T2.5 3-проходный синтез финального ответа (опционально в Tier 2)
**Проблема.** Финальный ответ местами рыхлый, приоритет измеренных чисел не гарантирован.

**Решение.** Перед выдачей — короткая цепочка draft→critique→refine с приоритетом измеренных индикаторов (числа/`block_id` из наблюдений) над общими формулировками; fail-open (всегда коммитим конкретный ответ).

**Файлы.** `agent.py` (новый `_synthesize`), `prompts.py`.
**Усилие.** Средне-высоко (2–3 LLM-вызова). **Риск.** Средний (стоимость/латентность). **Источник.** fp2mp `nodes/synthesis.py` (draft→critique→refine, 7-секционное memo, приоритет измеренного).
